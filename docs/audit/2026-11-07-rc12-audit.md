## 1. 🔴 阻断性问题（批次 1：`download` 队列调度层）

本轮范围只到队列调度：`DownloadQueue` / `DownloadStore` / `DownloadWorker`。
`ChunkDownloader` / `M3u8Downloader` / `MediaProbe` 留到批次 1b。

### 1.1 `processQueue()` 把「本进程正在跑」的任务改回「排队中」

- 位置：`download/src/main/java/cn/olfact/download/queue/DownloadQueue.kt:213`
- 问题：方法开头把**所有** `RUNNING` 记录改写成 `QUEUED`（理由写的是「进程重启，自动续传」）。
  但这个函数有两个入口：`DownloadWorker` 和界面里的 `kick()`，它们会同时调。
  第二次进入时，第一条任务正在跑（`activeIds` 里有它），记录却被改成 `QUEUED`。
- 为什么：`runOne` 见到 `activeIds` 已占用会直接 `return`，于是这条记录在整个下载期间都停在
  `QUEUED`——列表显示「排队中」、进度条不动，`speedOf` 也只对 `RUNNING` 返回速度。
  真下载和 UI 状态彻底脱节；此时杀进程，下次启动才会「续传」成功，用户看到的是随机行为。
- 修复：**已修**。抽出纯函数 `requeueCandidates(records, active)`：只转换「上次进程留下的」
  `RUNNING`，跳过 `activeIds` 里的 id；系统下载器任务（带 `systemDownloadId`）保持 `RUNNING` 继续跟踪。
  回归用例：`RequeueCandidatesTest`（6 例，含「系统引擎但丢了 downloadId 仍需续传」这种边界）。

### 1.2 删除记录后，迟到的失败回写会让任务「复活」

- 位置：`DownloadQueue.kt:262-270`（异常分支）
- 问题：`remove()` 的顺序是「先删记录 → 再 `job.cancel()`」。取消是协作式的，正在阻塞的
  OkHttp 调用不会立刻停，之后抛 `IOException` 走进 `catch (e: Exception)`，无条件
  `store.upsert(failed)` 把刚删掉的记录又写回队列。
- 为什么：用户删了一条下载，几秒后它带着「失败」重新出现在列表里，点进去文件路径指向已删的目录。
  完成路径原本有 `store.get(id) == null` 的保护（注释也写了「别把结果写回去」），异常路径漏了同一层判断。
- 修复：**已修**。异常分支先判 `store.get(id) == null`，命中就只 `publish()` 后返回。

## 2. 🟡 建议修复

### 2.1 `remove()` 在调用线程删产物目录

- 位置：`DownloadQueue.kt:127-141`
- 问题：`DownloadPaths.workDir(...).deleteRecursively()`、`SystemDownloader.cancel()`、
  `store.remove()`（内部全量重写 queue.json）全在调用线程执行，而调用方是列表页/详情页（主线程）。
- 为什么：m3u8 任务的临时目录可能躺着上千个分片，主线程递归删除就是一次 ANR；
  队列文件随着记录变多也会越来越慢（每条记录都要重新序列化整个列表）。
- 修复：**部分已修**——产物删除与系统任务取消移进 `scope.launch`（IO），失败记日志；
  记录状态仍在调用线程改（保证 UI 立即反馈）。**剩余**：`store.remove/upsert` 的写盘也应挪进 IO
  （见 2.4），需要改 `DownloadStore` 调用方，留到批次 1b 一并处理。

### 2.2 `activeIds` 存在只加不减的路径

- 位置：`DownloadQueue.kt:242`（旧 `jobs[id] = currentCoroutineContext()[Job] ?: return`）
- 问题：拿不到 `Job` 时直接 `return`，跳过 `finally`，`activeIds` 里的占位永远留着。
- 为什么：一旦发生，这条任务之后所有 `runOne` 都会被 `activeIds.add(id)` 挡掉，
  表现为「点继续没反应」，只能重启进程。
- 修复：**已修**。先取 `Job`，为空时 `activeIds.remove(id)` 再返回。

### 2.3 `processQueue()` 的返回值与实际处理条数不符

- 位置：`DownloadQueue.kt:225`（`queued.size`）
- 问题：实际处理的是 `queued + tracking`（系统任务跟踪），返回值只算 queued。
- 为什么：`DownloadWorker` 用返回值判断「还有没有活」；全是要跟踪的系统任务时返回 0，
  调用方会误判队列已空。
- 修复：返回 `ids.size`（或改成返回处理明细）。影响面小，安排在批次 1b 与 Worker 一起改。

### 2.4 每次 `upsert` 都全量重写 JSON

- 位置：`download/src/main/java/cn/olfact/download/queue/DownloadStore.kt:51-56`
- 问题：`JsonDownloadStore.upsert()` 改一条记录就把整个 map 序列化落盘（temp + rename）。
- 为什么：100 条历史 + 3 条并发下载时，每次进度落盘（800ms 一次 × 3 任务）都要重写整份文件；
  记录堆到几百条后写放大明显，还会和读路径抢同一把锁。
- 修复：加 dirty 标记 + 合并写（`upsert` 只标脏，后台每 800ms 落一次盘，`remove/终态` 立即落盘）；
  或换 Room（`DownloadStore` 已经是接口，B1 的单库落地时一起做）。

## 3. 🔵 可选优化

### 3.1 三个没有任何调用者的接口方法

- 位置：`DownloadStore.markAllRunningAsPaused()` / `nextQueued()` / `activeCount()`

- 为什么：接口即契约，留着会让人以为还有别的调度路径，读代码时要多花时间确认「谁在调」。

## 4. 🟢 做得好的地方

- `deleteArtifact()` 只允许删下载目录内的文件（`canonicalFile` + 前缀比较），
  `queue.json` 被手改坏也删不到别处——这是上一轮最有价值的一条硬化，位置在 `DownloadQueue.kt:143`。
- 系统任务丢失有上限（`MAX_MISSING_POLLS = 5`），不会无限轮询；`runSystem` 的注释把「为什么不能 continue」写清了。
- 进度节流分三层（UI 200ms / 落盘 800ms / 通知跟随落盘），终态走 `publish()` 不走节流，
  「卡在 99%」这类问题被结构性消掉了。
- `CancellationException` 与普通异常分开处理，且取消/暂停分支都判断了「记录是否还 RUNNING」，
  说明作者已经意识到状态机竞态——1.2 只是漏了同一个思路的一半。

### 6.1 655 行单文件装 8 个类型（🔴 → 已拆）

- 位置：`app/src/main/java/cn/olfact/app/data/ModuleBackends.kt`（拆分前 655 行）

  `DohAdapter`、`AdBlockAdapter`、`ScriptAdapter`、`AiAdapter`、`DownloadAdapter`，
  外加 DoH 模式映射与 `openExternal`。任何一处改动都要在 8 个类型之间滚动。
- 为什么：这是 app 层唯一集中了 5 个子系统适配的文件，也是合并期「契约不一致」的缓冲层。
  它越大，越容易变成「什么都往里塞」的回收站——本轮就已经看到 DoH 策略（自定义上游解析、
  模式映射）住在这里，而它本该跟着 `web/doh` 走、并且可以单测。
- 修复：**已拆成 9 个文件，一个文件一个职责**：
  `BackendInstall.kt`（装订与后台初始化）、`SnifferSink.kt`、`InjectionBus.kt`、
  `DohAdapter.kt`、`AdBlockAdapter.kt`、`ScriptAdapter.kt`、`AiAdapter.kt`、
  `DownloadAdapter.kt`（含 `toTask`）、`ExternalIntents.kt`（`openExternal`）。
  `package` 不变，调用方零改动。**未做**：把 `DohAdapter` 的策略部分（自定义上游解析、模式映射）
  挪进 `web/doh/DohPolicy` 并补单测——那要动模块边界，放到批次 3 与 DoH 一起做。

### 6.2 添加下载失败时静默无反馈（🔴 → 已修）

- 位置：`app/src/main/java/cn/olfact/app/data/DownloadAdapter.kt:28-55`
- 问题：`scope.launch { runCatching { facade.enqueue(...) } }`，失败被 `runCatching` 吞掉，
  没有日志也没有提示。
- 为什么：入队会真的失败——下载目录不可写、`queue.json` 损坏、spec 里 URL 非法。
  用户点「下载」后什么都没发生，只会以为 App 卡了，然后反复点。
- 修复：**已修**。`DownloadAdapter` 拿 `applicationContext`，失败时
  `Log.w` + 主线程 `Toast「添加下载失败：<原因>」`。

### 6.3 `DohAdapter.config()` 的 `enabled` 恒为 true（🟡 → 已修）

- 位置：`app/data/DohAdapter.kt:150`
- 问题：无论 DoH 是否在跑，`config().enabled` 都返回 `true`。
- 为什么：这是给设置页渲染状态开关的契约。今天还没人调（`grep` 确认 `config()` 零调用），
  但一旦接上，界面会永远显示「已开启」，用户关不掉也看不出来。
- 修复：**已修**。改为 `impl.status().running`。

### 6.4 `ScriptAdapter.all()` 每次渲染都把全部脚本体读进内存（🟡，未修）

- 位置：`app/data/ScriptAdapter.kt:22-32`
- 问题：`store.list()` 之后对每个脚本 `store.body(id)`，返回的 `UserScript.code` 带全文。
- 为什么：脚本管理页只需要 name/matches/enabled；装了 10 个 200KB 的脚本，
  一进列表就要读 2MB 文件、生成 2MB 字符串，且在主线程（`all()` 由 Fragment 直接调用）。
- 修复：给 `core/api/ScriptStore` 加 `fun code(id: String): String?`，
  `all()` 里 `code` 返回空串；编辑器打开时再按 id 取。属于跨模块契约变更，排批次 3。

### 6.5 `AiAdapter.all()` 逐个解密 API Key（🟡，未修）

- 位置：`app/data/AiAdapter.kt:12-22`
- 问题：列表映射时对每个供应商调 `store.apiKey(p)`（Keystore 解密），把明文塞进 `AiProvider.apiKey`。
- 为什么：供应商列表、备份导出、下拉选择都只需要 id/name/model；逐个解密既慢（Keystore 调用是 IPC），
  又把明文密钥扩散到 UI 层对象里，和上一轮「编辑时不再明文回显」的努力方向相反。
- 修复：`all()` 返回 `apiKey = ""`；新增 `ProviderStore.apiKeyOf(id)` 供编辑器按需取。
  排批次 3（和 6.4 一起做一次契约变更更划算）。

### 6.6 `clearFinished()` 逐条删除，每条都重写队列文件（🟡，未修）

- 位置：`app/data/DownloadAdapter.kt:66-72` + `DownloadStore.upsert/remove`
- 问题：N 条已完成记录 → N 次 `facade.remove()` → N 次全量 JSON 落盘 + N 次 `publish()`。
- 为什么：清空 200 条历史时等于写 200 次队列文件、推 200 次列表，删除按钮会明显卡顿。
- 修复：队列加 `removeAll(ids, deleteFile=false)` 批量接口（一次落盘、一次 publish）。排批次 3。

## 7. 批次 3：`web/doh`（🟡 → 已修 1 条 🔴）

范围：`TunnelProxy`（L2 本地隧道）、`UpstreamPool`、`DohManagerImpl` 的调用路径。
`DnsMessage` / `DnsRules` 纯解析层留到批次 3b。

### 7.1 多 A 记录兜底形同虚设：同一个 Socket 连两次（🔴 → 已修）

- 位置：`web/src/main/java/cn/olfact/web/doh/TunnelProxy.kt:250-272`（`connectUpstream`）
- 问题：解析出一个地址列表后，**复用同一个 `Socket` 实例**依次 `connect()` 前两个地址；
  第一次 `connect()` 失败后 Socket 已不可再用，第二次必然抛异常。
- 为什么：注释写的是「取前两个地址重试」，实际只有第一个地址有效。国内网络里
  「A 记录第一条被墙 / 超时、第二条可用」是最常见的场景——DoH 解析成功、隧道却建不起来，
  用户看到的是整站打不开，而日志只报最后一条错误，很容易被误判成「DoH 坏了」。
- 修复：**已修**。每个地址新建一个 `Socket`，失败即关闭；成功才登记进 `sockets`。
  没有加单测：要复现得伪造两个可达性不同的地址，JVM 单测成本高，留真机复核
  （换一个 A 记录第一条不可达的域名，看能否建连）。

### 7.2 上行转发超时后任务不取消（🟡 → 已修）

- 位置：`TunnelProxy.kt:288-292`（`pipeBoth`）
- 问题：`upload.get(30, SECONDS)` 超时只被 `runCatching` 吞掉，任务继续挂在 `copyPool` 里，
  往已经关闭的流写。
- 为什么：`copyPool` 是无界缓存池，卡住的任务会一直占着线程和两个 Socket 引用；
  隧道开久了线程数只涨不降。
- 修复：**已修**。`onFailure { upload.cancel(true) }`，中断阻塞的 `read`，让 `copy` 的 finally 收尾。

### 7.3 处理池 64 固定、没有背压（🟡 未修）

- 位置：`TunnelProxy.kt:80-84`（`Executors.newFixedThreadPool(POOL_SIZE)`）
- 问题：池满后任务进无界队列，`acceptLoop` 继续 accept 并 `execute`，客户端得不到任何响应，
  表现为「网页一直转圈」而不是明确失败。
- 为什么：一条隧道在下行 `copy` 里阻塞整个处理线程；同一个页面 6 条并发连接、
  几个标签页就能吃满 64，超出的请求既不报错也不超时（只有 30s idle 会兜底）。
- 修复：换成有界队列的 `ThreadPoolExecutor`（队列 128），拒绝时直接 `respond(503)` 并关连接；
  或把下行 `copy` 也挪进 `copyPool`、处理线程只做调度。两条都不大，但要重新做并发压测，
  单独立一批。

### 7.4 `raceAndSelect()` 用 `runBlocking` 实现（🔵 未修）

- 位置：`web/src/main/java/cn/olfact/web/doh/UpstreamPool.kt:67-74`
- 问题：公开 API 是阻塞签名，内部用 `runBlocking` 包 `async/awaitAll`。
- 为什么：当前两个调用点都在协程里（`reraceAsync()` 的 `scope.launch` 与测试），没炸；
  但签名本身邀请别人在 UI 线程调，最慢要等 2.5 s。
- 修复：改 `suspend fun raceAndSelect()`，`reraceAsync` 直接 `scope.launch { raceAndSelect() }`，
  测试改用 `runTest`。纯签名变更，风险低。

### 7.5 IPv6 字面量 CONNECT 会解析失败（🔵 未修）

- 位置：`TunnelProxy.kt:196-198`
- 问题：`authority.substringBeforeLast(':')` 对 `[2606:4700::1]:443` 得到 `[2606:4700::1]`，
  带方括号交给 `InetAddress.getByName` 会失败。
- 为什么：少见但真实（部分 CDN 会返回 IPv6 字面量重定向），失败时只会得到 502。
- 修复：`authority.startsWith("[")` 时取 `substringAfter('[').substringBefore(']')`。

### 7.6 🟢 做得好的地方

- 处理池与转发池分开，注释把「共用池会自锁」写清了——这是这类隧道最典型的死法，作者已经绕开。
- 只代理 80/443，其余端口直接 403；`handle()` 有 idle 超时、`readHeader` 有 16KB 上限并按字节匹配
  `CRLFCRLF`，没有「读一行等半天」的实现。
- `healthCheck()` 用自连做存活检查，比看线程状态靠谱。
